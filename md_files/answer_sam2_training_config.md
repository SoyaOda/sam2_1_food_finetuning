データ拡張ロジックと学習コードの分離このアーキテクチャがもたらす重要な利点は、データ拡張のロジックが学習スクリプト (train.py) から完全に分離されている点です。train.py は、YAMLファイルの transforms キー以下に何が定義されているかを関知せず、単にHydraによって構築された変換オブジェクトのリストを受け取り、データに適用するだけです。この設計は、研究開発において極めて高い柔軟性を提供します。例えば、単純なフリップから、MixUpやCutMixのような高度な拡張手法に切り替える際も、Pythonコードの変更は一切不要で、YAML設定ファイルを修正するだけで済みます。さらに、ある実験で使用された正確な前処理・拡張パイプラインが設定ファイル内に完全に記録されるため、実験の再現性が大幅に向上します。これは、現代のMLOpsにおけるベストプラクティスであり、ユーザーはこの柔軟性を最大限に活用することが推奨されます。第4章：戦略的なパラメータ凍結とオプティマイザ設定ファインチューニングの成功は、どのモデルパラメータを、どの程度の学習率で更新するかという最適化戦略に大きく依存します。SAM2.1の学習フレームワークは、Hydraを通じてこれらの戦略を柔軟に設定する機能を提供しており、特にVision Encoderとそれ以外の部分で異なる学習率を適用する「差分学習率（Differential Learning Rates）」が重要な役割を果たします。オプティマイザとスケジューラの設定YAML設定ファイル内の optimizer および lr_scheduler セクションは、最適化アルゴリズムとその学習率スケジュールを定義します。_target_ キーを用いて、torch.optim.AdamW のようなPyTorchのオプティマイザクラスを指定し、lr や weight_decay といったハイパーパラメータを渡すことができます 13。同様に、torch.optim.lr_scheduler.StepLR のような学習率スケジューラも設定可能です 14。YAMLoptimizer:
  _target_: torch.optim.AdamW
  lr: ${optimizer.base_lr} # base_lrを参照
  weight_decay: 0.01

lr_scheduler:
  _target_: torch.optim.lr_scheduler.StepLR
  step_size: 1
  gamma: 0.9
差分学習率によるファインチューニングMOSEのファインチューニング設定 (sam2.1_hiera_b+_MOSE_finetune.yaml) には、base_lr と vision_lr という2つの学習率が定義されています 6。これは、差分学習率戦略が採用されている明確な証拠です。この戦略の背景にある考え方は、ImageNetなどで大規模に事前学習されたVision Encoder（HieraのようなVision Transformer）は、既に強力な特徴抽出能力を獲得しているため、ごくわずかな学習率で微調整（ファインチューニング）するのが望ましいというものです。一方で、マスクデコーダやその他の比較的小さなコンポーネントは、新しいタスクに対してより速く適応させるために、高めの学習率で学習させます。param_groups の活用メカニズムこの差分学習率を実現しているのは、PyTorchのオプティマイザが持つ param_groups という機能です 15。YAMLで定義された base_lr や vision_lr は、SAM2Train モデルクラス内の configure_optimizers というメソッド（これはPyTorch Lightningなどのフレームワークで一般的なパターンです）によって解釈されます。このメソッドは、モデルのすべてのパラメータ (model.named_parameters()) を走査し、パラメータ名に基づいて、それがVision Encoderに属するものか、それ以外の部分（デコーダなど）に属するものかを判断します。そして、それぞれを異なる「パラメータグループ」にまとめ、各グループに異なる学習率（vision_lr または base_lr）を設定した上で、オプティマイザに渡します。パラメータの凍結方法特定のレイヤー群（例えば、Vision Encoder全体）を学習中に更新しないように「凍結」させたい場合、最も直接的な方法は、そのパラメータグループの学習率をゼロに設定することです。YAMLファイルで vision_lr: 0.0 と指定すれば、Vision Encoderの重みはオプティマイザによって更新されなくなり、事実上凍結されます。また、configure_optimizers メソッドの実装によっては、freeze_encoder: true のようなブール値のフラグをYAMLで設定し、該当するパラメータをオプティマイザに渡すリストから完全に除外する、というロジックが組まれている可能性もあります。具体的な挙動については、training/model/sam2_train.py 内の SAM2Train クラスの実装を確認することが推奨されます。モデルと設定ファイルの密結合vision_lr のようなキーは、torch.optim.AdamW の標準的な引数ではありません。これは、YAML設定ファイルと SAM2Train という特定のPythonクラスの間に「暗黙の契約」が存在することを示しています。つまり、このYAMLは汎用的なものではなく、SAM2Train クラスの configure_optimizers メソッドがこれらのカスタムキーを特別に解釈するように設計されているのです。この事実は、ユーザーがオプティマイザ設定を、異なるモデルアーキテクチャ間で単純にコピー＆ペーストできる汎用的なブロックとして扱えないことを意味します。もしユーザーがHiera ユーザーがYAML設定ファイルに相対パス（例: dataset: img_folder:../../my_data/images）を記述した場合、このパスはスクリプトを起動したディレクトリからではなく、Hydraが新たに作成した出力ディレクトリ (outputs/.../) を基準に解決されます。その結果、意図したデータセットの場所を見つけることができず、エラーが発生します。単純な解決策: 最も簡単で確実な解決策は、絶対パス（例: /home/user/sam2_project/my_data/images）を使用することです。絶対パスは現在の作業ディレクトリに依存しないため、Hydraのディレクトリ変更の影響を受けません。高度な解決策：Hydraリゾルバ: より柔軟でポータブルな解決策として、Hydraはパス管理のための組み込み関数（リゾルバ）を提供しています。${oc.env:VAR_NAME}: PWD のような環境変数を参照できます。例えば ${oc.env:PWD} は、スクリプト実行時の元の作業ディレクトリを取得します。${hydra:runtime.cwd}: スクリプトが起動された元のディレクトリのパスを取得します。これは多くの場合、最も堅牢で推奨される方法です。以下に、データパスを指定する際の具体例を示します。YAMLdataset:

  # img_folder:../data/images

  # img_folder: /path/to/your/project/data/images

  # 正解 (Hydraリゾルバ): 堅牢で移植性が高い、推奨される方法
  img_folder: ${hydra:runtime.cwd}/data/images
  gt_folder: ${hydra:runtime.cwd}/data/masks
